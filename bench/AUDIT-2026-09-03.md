## 二、高优问题详情

### 1. 折线图 X 轴档位过期（新档位必崩）

- 位置：`bench/web/tpl/ctrl.js:324`
- 现状：
  ```js
  var TIERS = [50, 100, 200, 400, 800, 1600, 3200, 6400];
  ```
- 根因：`drawRampChart` 的 X 轴槽位来自固定 TIERS 与实际档位求交集（`present`）。新档位 `[50,500,2000,5000,8000,...,50000]` 与旧 TIERS 只交集出 `[50]` 一个槽位；其余档位 `lx()` 走 `indexOf<0 → return padL`，**全部数据点堆在图表左边缘**，50 单独居中，图完全不可读。
- 影响：对比页 SVG 曲线报废（JSON 数据本身完好）。
- 修复：把 TIERS 改为与两引擎一致的 15 档：
  ```js
  var TIERS = [50, 500, 2000, 5000, 8000, 12000, 16000, 20000, 24000, 28000, 32000, 36000, 40000, 45000, 50000];
  ```
  或更稳：直接从 `all.map(l=>l.count)` 去重排序生成 `present`，删掉硬编码。
- 状态：✅ **已修（2026-09-04）** —— `present` 改为从实际数据动态去重排序生成，TIERS 硬编码已删除

### 2. Cocos ramp 结果丢失 `invalidCurve`，污染曲线闸门对 Cocos 失效

- 位置：`proj-cocos-3d/assets/scripts/FishBench3D.ts:296-300`（onDone 组装 result）
- 现状：
  ```ts
  const result = { meta: {...}, cap: r.cap, jankAt: r.jankAt, capped: r.capped, levels: L };
  ```
  bench-runner `autoRamp` 的 `onDone` 明确给了 `invalidCurve`（`bench-runner.js:183`），FishBench3D 组装时**没有带上**。
- 对照：Laya 侧 `Main.ts:711` 的 result 包含 `invalidCurve` ✓。
- 影响：`ctrl.js:244-245` 的 `wgValid/glValid` 检查 `!r.invalidCurve` —— Cocos 恒 undefined → 恒通过。「低档掉帧后高档恢复稳定」的受污染曲线不会被标记无效，跨后端结论可能基于脏数据。
- 修复：`onDone` 里补 `invalidCurve: r.invalidCurve`（一行）。
- 状态：✅ **已修（2026-09-04）** —— result 增加 `invalidCurve`，顺带聚合运行时后端（见 #3）

### 3. Cocos WebGPU 静默回退时对比有效性放行

- 位置链：`FishBench3D.ts:298`（meta.backendValid）→ `ctrl.js:242-245`
- 现状：
  - `FishBench3D.ts` onDone 的 `meta.backendValid = requested !== 'webgpu' || backend === 'webgpu'`，其中 `backend` 来自 `this.backend()`——**是发起点的一次性读数**，且 `meta.backend` 传的就是这个值；
  - 逐档的**运行时真实后端**（`gfxAPI===8`，含 WebGPU 臂回退 WebGL 的如实标注）在 `levels[i].actualBackend` 里有（`FishBench3D.ts:291`），但没有聚合成 ramp 级字段；
  - `ctrl.js finishRampCompare` 的 `wgReal = wg.meta.backend`（请求值，非运行时值），`wgValid` 依赖 `meta.backendValid`。
- 场景：WebGPU 臂构建后 requestAdapter 为 null → renderMode:4 回退 WebGL → 若发起时 `backend()` 已如实返回 webgl，则 meta.backend='webgl'，ctrl 会拦 ✓；**但若回退发生在运行中途/逐档间（驱动重置等），发起读数是 webgpu，全程实际 webgl，则不拦**。
- 对照：Laya 侧 `meta.backend = actualBackend()`（finish 时读）✓ 无此问题。
- 修复（两处任一）：
  1. FishBench3D onDone 聚合：`const actuals = [...new Set(L.map(l=>l.actualBackend))]; meta.backendValid = actuals.length===1 && actuals[0]===backend; meta.backend = actuals[0] || backend;`
  2. ctrl 侧改用 `r.levels[0].actualBackend` 做 `wgReal/glReal`。
- 状态：✅ **已修（2026-09-04）** —— 采用方案 1：`onDone` 聚合 `actuals`（唯一运行时后端）写入 `meta.backend`，`backendValid` = 全程实际后端一致 且 WebGPU 臂未回退；HUD 文案同步。

### 4. Laya 3D 采样把后台切回的钳制帧计入样本

- 位置：`laya-proj-3d/src/Main.ts:115`（`dt = min(now-lastFrame, 100)`）+ `Main.ts:151`（`samples.push(dt)` 无条件）
- 根因：后台标签 rAF 冻结，切回第一帧真实间隔可能是数秒；Laya 钳到 100ms 后**照 push 进 samples**。一次切后台 = 一枚 100ms 假样本。采样窗仅 6s（≈360 帧），几枚 100ms 就能把 p95/p99 顶上去，触发误判掉帧。
- 对照：
  - `stats.js:51`：`dt<=0 || dt>1000` 直接丢 ✓（但 100~1000ms 仍收，见 #16 共同问题）；
  - Cocos 走 stats.js，无此 100ms 钳制污染。
- 影响：Laya 各档 p95/p99/jank 判定可能被「用户切了下标签页」这种无关事件污染 → cap 虚低。总控 iframe 场景用户通常会盯着看，风险中等；手动单页测试时真实存在。
- 修复：采样期 `if (dt > 200) return;`（与 stats.js 口径对齐或更严），预热期不变。
- 状态：✅ **已修（2026-09-04）** —— 采样期 `dt > 200` 丢弃（样本与 drawCall 均不收），墙钟计时不受影响

## 三、中优问题详情

### 5. 判定/采样逻辑双实现（漂移风险）

- `bench-runner.js autoRamp`（Cocos 用）与 `Main.ts runRamp/runFixed`（Laya 自实现）是两份独立实现，以下常量/行为两处维护：
  - 稳定判定 `fps>=55 && (p95>0 ? p95<=18.2 : true)`
  - 掉帧判定 `fps<50 || p95>=33.4`
  - 档位表（本次已同步 15 档）、预热 5s/采样 6s、首档×2、重试×2、跑完不终止
- 本次审计确认**当前两份一致**，但历史上已经漂移过一次（Laya 早期无 p95 判定）。
- 建议：Laya 3D 迁移到 sim-core `BenchRunner`（像 Cocos 那样实现 adapter 契约），或至少把阈值抽成 `sim-core/bench-consts.js` 双方引用。
- 状态：**未修**（结构性改造）

### 6. GPU 信息探针可能报错 GPU / WebGPU 臂报 WebGL 值

- 位置：`stats.js:100-123`（captureGpuInfo 新建一次性 canvas）、`Main.ts:631-646`（gpuInfo 同样新建 canvas）
- 问题：
  1. 探针 canvas 与引擎 canvas 是两个独立 GL 上下文 —— 双显卡（iGPU+dGPU）笔记本上 Chrome 可能给两个上下文分配**不同 GPU**，`gpuVendor/gpuRenderer` 报的是探针那块，不是实际渲染那块；
  2. LayaX WebGPU 臂上，`Main.ts gpuInfo()` 仍走 WebGL 探针 → JSON 里 gpuRenderer 显示 WebGL 字符串，**不是 WebGPU adapter.info**，会误导「两臂是否同 GPU」的核对；
  3. 每个 fixedRun 调一次（ramp 15 次 = 15 个一次性 GL 上下文），有 GC/驱动开销。
- 建议：
  - 优先从**引擎自己的上下文**取（Cocos：`director.root.device.gl`；Laya WebGL：引擎 canvas 的 gl）；
  - WebGPU 臂记录 `adapter.info`（vendor/architecture）；
  - 每页只采一次缓存。
- 状态：**未修**

### 7. 抗锯齿（MSAA）矩阵不对称

- 事实链：
  - `laya-proj-3d/release/web/js/index.js`：`"isAntialias":true` —— build.js 只对 **2D vendor 臂**（laya/laya-webgl）patch 关闭，**laya3d 两臂没 patch**；
  - Cocos 3D：settings.json / index.html / 主 bundle 全文无 `antialias` 字样 → WebGL 上下文用浏览器默认 `antialias:true`（MSAA 通常 4x）；
  - WebGPU 两臂（Cocos renderMode:4 / LayaX）：单采样，无 MSAA。
- 矩阵：
  | 臂 | MSAA |
  |----|------|
  | Cocos3D WebGL | 开（默认） |
  | Laya3D WebGL | 开（isAntialias:true） |
  | Cocos3D WebGPU | 关（单采样） |
  | Laya3D WebGPU | 关（单采样） |
- 结论：**跨引擎（同后端）对比公平** ✓；**引擎内 WebGL vs WebGPU 对比偏向 WebGPU**（像素填充/显存带宽少一次 resolve）。3D 水族馆是填充敏感场景，此偏差不可忽略。
- 建议：spec §7 的「antialias 关」原则落到 3D —— build.js 给 laya3d WebGL 臂 patch `isAntialias:false`；Cocos 3D 显式传 `antialias:false`（或在 spec 明确登记「3D 场景 WebGL=MSAA on / WebGPU=single」作为已知偏差，解读数据时扣除）。
- 状态：**未修**（需先决策统一方向）

### 8. 臂执行顺序固定且两处相反

- `ctrl.js autoCompare`：`order = [webgpu, webgl]`（先 WebGPU）；
- `ctrl.js fullRun`：`backends = [webgl, webgpu]`（先 WebGL）。
- 影响：后跑的臂承受更热 GPU（节流）→ 自动对比系统性偏向先跑臂；且两功能偏差方向相反，交叉解读困难。
- 建议：顺序交替（按时间戳奇偶）或随机，并把执行顺序写进结果 JSON（`meta.armOrder`）。
- 状态：**未修**

### 9. 过渡期陷阱：旧引擎产物 + 新总控逻辑

- 新档位（15 档）/新判定（跑完不终止）在 `FishBench3D.ts`、`Main.ts` 里，需要：
  1. Cocos Creator 重建 → 拷贝到 `bench/web/vendor/cocos3d/`（**build.js 读的是 vendor，不是 build/web-mobile-XXX**）；
  2. LayaAir IDE 重建 → `laya-proj-3d/release/web/`（build.js 直读该目录 ✓）。
- 未重建时 dist 仍跑旧 24 细档：24×11s=264s + 多次重试(16s/次) > 总控 330s 窗口 → `__benchLastResult` 未产出 → cap=0「假故障」复现（即之前截图那次的根因）。
- 状态：**等用户重建**（build.js/sim-core 侧已就绪）

## 五、备忘（方法论 / 待实测）

### 16. 采样窗 100~1000ms 间隙帧计入（两引擎共同）
`stats.js:51` 只丢 `dt>1000`。0.1~1s 的卡顿（窗口切换半程、GC 大停顿）会以原值进 samples。p95 抗这类低频长尾其实较强（数百帧里占比 <5%），但 p99/p1Low 会被打穿。建议采样期 >200ms 丢弃或单列 `outlierFrames` 字段。

### 17. LayaX WebGPU 臂 drawCall 未知 ⚠ 待实测
`Main.ts readDrawCalls` 走 `LayaGL.statAgent` 的 `CT_3DDrawCall`。已确认 `laya.webgpu_3D.js` 里有 `statAgent=new t.DefaultSta...` 注册 ✓，但 LayaX 新管线是否给 `CT_3DDrawCall` 计数**未实测**。若返回 -1，结果里 `drawCallAvg` 会是 0（`dc>=0` 过滤后 drawCalls 数组为空，average=0）——**注意 dc=0 与 dc=-1 的语义混淆**。实测方法：WebGPU 臂跑一档看 HUD dc 值。

### 18. 直接开页 vs 总控 iframe 的画布口径
引擎页直开 = 独占窗口（画布=窗口大小×DPR）；总控 iframe = 全屏内嵌（画布=视口）。填充负载因此不同。ctxLine 已输出 画布/DPR/GPU/填充MP ✓ —— **跨页比较必须核对 ctxLine 一致后才可横向比数字**。spec §7 #8 的「固定 1280×720」只在 iframe 路径下成立。

### 19. 重试机制剩余风险
每档最多重试 1 次。若某机器存在周期性后台任务（杀毒/更新）在两次窗口都触发，仍会误判。现有 p95 化 + 动态预热已把概率压低；如再遇疑似，靠「完整逐档曲线 + invalidCurve」人工判读（这正是 #2 修复必须落地的原因）。
